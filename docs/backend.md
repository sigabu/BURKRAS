# Подключение сервера после демо

Сейчас `config.DEMO_MODE = true`. Адаптер в `site/assets/leads.js` валидирует форму, возвращает `{ mode: 'demo', submitted: false }` и не выполняет сеть или хранение контактов. Калькулятор полностью работает в браузере. GitHub Pages хранит только статические файлы и не запускает сервер или БД.

## Точки подключения

1. `site/assets/config.js`: утверждённые контакты, тарифы, HTTPS URL сервера, флаг демо.
2. `site/assets/leads.js`: единая отправка `POST {API_URL}/leads`. Не подключать БД из браузера.
3. `site/assets/app.js`: раздельные подтверждения демо и реально принятой заявки.
4. `site/index.html`: пометка будущей загрузки фотографий.
5. `site/privacy.html`: заменить описание демо действующей политикой и согласиями владельца.

## Предлагаемый контракт

Тело JSON: `name`, `phone` (нормализованное `+7...`), `service` (`drilling`, `cutting`, `reinforcement`, `demolition`, `consultation`), `comment`, `estimate`, `source` (`contact`, `calculator`, `callback`), `consent`, `consentVersion`, `website` (поле-ловушка). Диапазон клиента — справочная информация; сервер пересчитывает по утверждённым тарифам и не доверяет цене из запроса.

Успех — `201` и `{ "id": "server-generated-id" }`. Только после получения ID интерфейс сообщает, что заявка принята. Ошибки: `400/422` валидация, `429` ограничение попыток, `5xx` сбой. Клиентский таймаут — 15 секунд. `Idempotency-Key` предусмотрен для исключения дубликатов; сервер должен сохранять ключ вместе с результатом. Клиент удерживает ключ в памяти формы при повторной попытке и сбрасывает при изменении или очистке формы.

## Сервер и БД

Статический фронтенд переносится на любой хостинг без изменения логики страницы. Сервер можно подключить отдельным сервисом. Конкретная платформа выбирается после уточнения требований владельца к размещению и обработке данных.

Минимальная схема для PostgreSQL описана в `backend/schema.sql` как проект, а не действующая миграция. Серверная часть отвечает за повторную валидацию телефона, длины текста, согласия, типа услуги и параметров расчёта; ограничение частоты; антиспам; идемпотентность; запись заявки и аудит статуса; доступ администратора.

Уведомления в почту или мессенджер отправляет сервер после сохранения. Ошибка уведомления не должна терять уже принятую заявку. Для этого можно использовать очередь уведомлений и повторные попытки.

## Фотографии и администрирование

При будущем добавлении фото: ограничить тип и размер, проверять содержимое на сервере, хранить отдельно от статического сайта с контролем доступа. Не загружать приватные фотографии клиентов в публичный репозиторий. Политика хранения и удаления должна охватывать вложения и контакты. Секреты, SMTP-пароли и токены хранятся только на сервере. CORS разрешает конкретный домен сайта, а не любой origin.

## Перед включением реальных заявок

- Получить действующие контакты, тарифы и реквизиты от владельца.
- Подготовить реальные политику и согласие, определить сроки хранения и операторов данных.
- Развернуть API и БД, проверить приём, ошибки, таймауты, дубликаты и уведомления.
- Указать API_URL, выключить DEMO_MODE, заменить все видимые демо-подписи, кнопки «Подготовить заявку» и удалить запрет индексации.
- Проверить доступность и адаптивность вновь. Добавить реальные фотографии и отзывы только с разрешением.

Это ориентир для реализации. Работающий backend и юридические документы в текущую демонстрацию не входят.
